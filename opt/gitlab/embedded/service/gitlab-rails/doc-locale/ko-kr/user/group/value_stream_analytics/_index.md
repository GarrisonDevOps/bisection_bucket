가치 흐름 분석은 소프트웨어 개발 프로세스의 각 단계별 소요 시간을 계산합니다. 병합 요청 또는 이슈 이벤트를 추적하여 아이디어에서 프로덕션까지 소요되는 시간을 측정할 수 있습니다.

가치 흐름 분석을 사용하여 다음을 파악합니다:

- 아이디어에서 프로덕션까지 소요되는 시간입니다.
- 주어진 프로젝트의 속도입니다.
- 개발 프로세스의 병목 현상입니다.
- 오래 실행되는 이슈 또는 병합 요청입니다.
- 소프트웨어 개발 생애 주기가 느려지는 요인입니다.

가치 흐름 분석은 기업을 다음에서 지원합니다:

- 엔드투엔드 DevSecOps 워크스트림을 시각화합니다.
- 비효율성을 파악하고 해결합니다.
- 워크스트림을 최적화하여 더 많은 가치를 더 빠르게 제공합니다(예: [병합 요청 검토 시간 단축](https://about.gitlab.com/blog/how-we-reduced-mr-review-time-with-value-stream-management/)).

[가치 흐름 관리 제품 투어](https://gitlab.navattic.com/vsm)를 보려면 클릭 데모를 참조하세요.

가치 흐름 분석은 계층 구조를 가지고 있습니다:

- **가치 흐름**은 가치 흐름 스테이지 목록을 포함합니다.
- 각 가치 흐름 스테이지 목록은 하나 이상의 **스테이지**를 포함합니다.
- 각 스테이지는 두 개의 **이벤트**로 정의됩니다: 시작 및 종료.

## 측정항목 {#metrics}

**개요** 페이지의 가치 흐름 분석은 프로젝트 및 그룹에 대한 DevSecOps 생애 주기 성능의 주요 측정항목을 표시합니다.

### 수명 주기 측정항목 {#lifecycle-metrics}

가치 흐름 분석은 다음 수명 주기 측정항목을 포함합니다:

- **리드 타임**: 이슈가 생성된 시점부터 종료된 시점까지의 중앙값 시간입니다.
- **사이클 타임**: 이슈가 병합 요청의 커밋 메시지에서 [처음 참조된](../../project/issues/crosslinking_issues.md#from-commit-messages) 시점부터 해당 참조 이슈가 종료된 시점까지의 중앙값 시간입니다. 커밋 메시지에 `#` 다음에 이슈 번호(예: `#123`)를 포함해야 합니다. 그렇지 않으면 데이터가 표시되지 않습니다. 병합 요청이 첫 번째 커밋 후에 생성되므로 사이클 타임은 일반적으로 리드 타임보다 짧습니다.
- **새 이슈**: 생성된 새 이슈의 개수입니다.
- **배포**: 프로덕션에 대한 배포의 총 개수입니다.

### DORA 측정항목 {#dora-metrics}

{{< details >}}

- 티어: Ultimate
- 제공 서비스: GitLab.com, GitLab Self-Managed, GitLab Dedicated

{{< /details >}}

가치 흐름 분석은 다음 [DORA](../../analytics/dora_metrics.md) 측정항목을 포함합니다:

- 배포 빈도
- 변경 리드 타임
- 서비스 복원 시간
- 변경 실패율

DORA 측정항목은 [DORA API](../../../api/dora/metrics.md)의 데이터를 기반으로 계산됩니다.

GitLab Premium 또는 Ultimate 구독이 있는 경우:

- 성공한 배포의 개수는 DORA 데이터로 계산됩니다.
- 데이터는 환경 및 환경 티어에 따라 필터링됩니다.

## 가치 흐름 {#value-streams}

가치 흐름은 고객에게 가치를 전달하는 전체 작업 프로세스입니다. 가치 흐름은 스테이지의 컨테이너 객체입니다. DevOps 생애 주기의 다양한 측면에 초점을 맞추기 위해 그룹당 여러 가치 흐름을 가질 수 있습니다.

## 가치 흐름 스테이지 {#value-stream-stages}

스테이지는 스테이지 이름 등의 추가 메타데이터가 있는 이벤트 쌍(시작 및 종료 이벤트)을 나타냅니다. 재정렬하고 숨길 수 있는 기본 제공 기본값 스테이지와 함께 가치 흐름 분석을 사용할 수 있습니다. 특정 개발 워크플로우와 일치하는 커스텀 스테이지를 생성하고 추가할 수도 있습니다.

## 가치 흐름 스테이지 이벤트 {#value-stream-stage-events}

{{< history >}}

- 병합 요청 첫 검토자 할당 이벤트가 GitLab 17.2에서 [도입](https://gitlab.com/gitlab-org/gitlab/-/issues/466383)되었습니다. GitLab 17.2 이전에 생성되거나 업데이트된 병합 요청의 검토자 할당 이벤트는 보고서에 사용할 수 없습니다.

{{< /history >}}

이벤트는 스테이지가 시작되고 종료되는 시기를 정의하는 구성 요소입니다. 각 이벤트에는 시작 시간과 종료 시간이 있습니다:

- 시작 이벤트 시간은 스테이지에서 작업이 시작될 때를 나타냅니다(예: 이슈가 생성될 때).
- 종료 이벤트 시간은 스테이지에서 작업이 완료될 때를 나타냅니다(예: 이슈가 종료될 때).

GitLab은 다음 공식을 사용하여 시작 및 종료 이벤트 시간에 따라 스테이지 기간을 계산합니다: 스테이지 기간 = 종료 이벤트 시간 - 시작 이벤트 시간

가치 흐름 분석은 다음 이벤트를 지원합니다:

- 이슈 종료
- 이슈 생성
- 보드에 처음 추가된 이슈
- 반복에 처음 추가된 이슈
- 처음 할당된 이슈
- 마일스톤과 처음 연결된 이슈
- 커밋에서 처음 언급된 이슈
- 추가된 이슈 레이블
- 제거된 이슈 레이블
- 병합 요청 종료
- 병합 요청 생성
- 처음 할당된 병합 요청
- 처음 커밋된 병합 요청
- 프로덕션에 처음 배포된 병합 요청
- 추가된 병합 요청 레이블
- 제거된 병합 요청 레이블
- 마지막으로 승인된 병합 요청
- 마지막 빌드 완료 병합 요청
- 마지막 빌드 시작 병합 요청
- 병합된 병합 요청
- 검토자가 처음 할당된 병합 요청

스테이지 이벤트에 대한 아이디어나 피드백을 [이슈 520962](https://gitlab.com/gitlab-org/gitlab/-/issues/520962)에서 공유할 수 있습니다.

## 스테이지 측정 {#stage-measurement}

가치 흐름 분석은 각 스테이지를 시작 이벤트부터 종료 이벤트까지 측정합니다. 종료 이벤트에 도달한 항목만 스테이지 시간 계산에 포함됩니다.

기본적으로 차단된 이슈는 생애 주기 개요에 포함되지 않습니다. 그러나 커스텀 레이블(예: `workflow::blocked`)을 사용하여 이를 추적할 수 있습니다.

미리 정의된 이벤트를 기반으로 가치 흐름 분석의 스테이지를 커스터마이즈할 수 있습니다. 구성을 돕기 위해 GitLab은 템플릿으로 사용할 수 있는 미리 정의된 스테이지 목록을 제공합니다. 예를 들어 이슈에 레이블을 추가할 때 시작되고 다른 레이블을 추가할 때 종료되는 스테이지를 정의할 수 있습니다.

다음 표는 가치 흐름 분석의 미리 정의된 스테이지의 개요입니다.

| 스테이지   | 측정 방법   |
| ------- | -------------------- |
| 이슈     | 이슈를 생성한 후 레이블 지정 또는 마일스톤에 추가하여 이를 해결하기 위한 조치를 취할 때까지의 중앙값 시간입니다(먼저 온 것이 우선). 레이블은 이미 [이슈 보드 목록](../../project/issue_board.md)이 생성된 경우에만 추적됩니다. |
| 플랜      | 이전 스테이지를 위해 수행한 작업과 브랜치에 첫 번째 커밋을 푸시할 때까지의 중앙값 시간입니다. 브랜치의 첫 번째 커밋은 **계획**과 **코드** 간의 분리를 트리거합니다. 브랜치의 최소 하나의 커밋에는 관련 이슈 번호(예: `#42`)가 포함되어야 합니다. 브랜치의 어떤 커밋도 관련 이슈 번호를 언급하지 않으면 스테이지의 측정 시간에 고려되지 않습니다. |
| 코드      | 첫 번째 커밋(이전 스테이지)을 푸시한 후 해당 커밋과 관련된 병합 요청(MR)을 생성할 때까지의 중앙값 시간입니다. 프로세스를 추적하는 핵심은 병합 요청 설명에 [이슈 종료 패턴](../../project/issues/managing_issues.md#default-closing-pattern)을 포함하는 것입니다. 예를 들어 `Closes #xxx`이며, 여기서 `xxx`은 이 병합 요청과 관련된 이슈의 번호입니다. 종료 패턴이 없으면 계산은 병합 요청의 첫 번째 커밋 생성 시간을 시작 시간으로 사용합니다. |
| 테스트      | 해당 프로젝트의 전체 파이프라인을 실행하는 중앙값 시간입니다. 이는 GitLab CI/CD가 해당 병합 요청에 푸시된 커밋에 대한 모든 작업을 실행하는 데 걸리는 시간과 관련이 있습니다. 기본적으로 모든 파이프라인에 대한 시작->완료 시간입니다. |
| 리뷰    | 종료 이슈 패턴이 있는 병합 요청을 검토하는 데 걸린 중앙값 시간이며, 생성 시점부터 병합될 때까지입니다. |
| 스테이징   | 종료 이슈 패턴이 있는 병합 요청을 병합한 후 [프로덕션 환경](#production-environment)에 처음 배포될 때까지의 중앙값 시간입니다. 프로덕션 환경이 없으면 이는 추적되지 않습니다. |

> [!note]
> 가치 흐름 분석은 타임스탬프 데이터에서 작동하며 스테이지의 최종 시작 및 종료 이벤트만 집계합니다. 여러 번 스테이지 사이를 오갔던 항목의 경우 스테이지 시간은 최종 이벤트의 타임스탬프에서만 계산됩니다.

### 프로덕션 환경 {#production-environment}

가치 흐름 분석은 다음 패턴과 일치하는 이름을 가진 프로젝트 [환경](../../../ci/yaml/_index.md#environment)을 찾아서 [프로덕션 환경](../../../ci/environments/_index.md#deployment-tier-of-environments)을 식별합니다:

- `prod` 또는 `prod/*`
- `production` 또는 `production/*`

이 패턴은 대소문자를 구분하지 않습니다.

GitLab CI/CD 구성에서 프로젝트 환경의 이름을 변경할 수 있습니다.

### 워크플로우 예시 {#example-workflow}

이 예시는 하루 동안 7개 스테이지 모두를 거쳐가는 워크플로우를 보여줍니다.

스테이지에 시작 및 종료 시간이 포함되지 않으면 해당 데이터는 중앙값 시간에 포함되지 않습니다. 이 예시에서는 마일스톤이 생성되었으며 테스트 및 환경 설정을 위한 CI/CD가 구성되었습니다.

- 09:00: 이슈 생성. **이슈** 스테이지가 시작됩니다.
- 11:00: 이슈를 마일스톤(또는 백로그)에 추가하고, 이슈에 대한 작업을 시작하고, 로컬로 브랜치를 생성합니다. **이슈** 스테이지가 종료되고 **계획** 스테이지가 시작됩니다.
- 12:00: 첫 번째 커밋을 수행합니다.
- 12:30: 이슈 번호를 언급하는 두 번째 커밋을 브랜치에 수행합니다. **계획** 스테이지가 종료되고 **코드** 스테이지가 시작됩니다.
- 14:00: 브랜치를 푸시하고 [이슈 종료 패턴](../../project/issues/managing_issues.md#closing-issues-automatically)을 포함하는 병합 요청을 생성합니다. **코드** 스테이지가 종료되고 **테스트** 및 **리뷰** 스테이지가 시작됩니다.
- GitLab CI/CD는 [`.gitlab-ci.yml` 파일](../../../ci/yaml/_index.md)에 정의된 스크립트를 실행하는 데 5분이 걸립니다.
- 19:00: 병합 요청을 병합합니다. **리뷰** 스테이지가 종료되고 **스테이징** 스테이지가 시작됩니다.
- 19:30: `production` 환경에 대한 배포가 완료됩니다. **스테이징**이 종료됩니다.

가치 흐름 분석은 각 스테이지에 대해 다음 시간을 기록합니다:

- **이슈**: 09:00~11:00: 2시간
- **계획**: 11:00~12:00: 1시간
- **코드**: 12:00~14:00: 2시간
- **테스트**: 5분
- **리뷰**: 14:00~19:00: 5시간
- **스테이징**: 19:00~19:30: 30분

이 예시와 관련하여 다음 관찰을 유념하세요:

- 이 예시는 첫 번째 커밋이 이슈 번호를 언급하지 않아도 상관없다는 것을 보여줍니다. 작업 중인 브랜치의 모든 커밋에서 나중에 이를 수행할 수 있습니다.
- **테스트** 스테이지는 사이클의 전체 시간 계산에 사용됩니다. 모든 MR을 테스트해야 하므로 **리뷰** 프로세스에 포함됩니다.
- 이 예시는 7개 스테이지의 하나의 사이클만 설명합니다. 가치 흐름 분석 대시보드는 여러 사이클에 대한 중앙값 시간을 표시합니다.

### 누적 레이블 이벤트 기간 {#cumulative-label-event-duration}

{{< history >}}

- [GitLab 16.9에 도입](https://gitlab.com/gitlab-org/gitlab/-/issues/432576)되었으며 [기능 플래그](../../../administration/feature_flags/_index.md)는 `enable_vsa_cumulative_label_duration_calculation` 및 `vsa_duration_from_db`로 명명되었습니다. 기본적으로 비활성화되었습니다.
- GitLab 16.10의 [GitLab.com 및 GitLab Self-Managed에서 활성화](https://gitlab.com/gitlab-com/gl-infra/production/-/issues/17476)되었습니다. 기능 플래그 `vsa_duration_from_db`이 제거되었습니다.
- 기능 플래그 `enable_vsa_cumulative_label_duration_calculation`이(가) GitLab 17.0에서 [제거](https://gitlab.com/gitlab-com/gl-infra/production/-/issues/17478)되었습니다.

{{< /history >}}

이 기능을 사용하면 가치 흐름 분석이 레이블 기반 스테이지에 대한 반복 이벤트의 기간을 측정합니다. 시작 및 종료 이벤트 모두에 대해 레이블 제거 또는 추가 이벤트를 구성해야 합니다.

예를 들어 스테이지는 `in progress` 레이블이 추가되고 제거되는 시점을 추적하며 다음 시간이 있습니다:

- 9:00: 레이블이 추가됨.
- 10:00: 레이블이 제거됨.
- 12:00: 레이블이 추가됨.
- 14:00 레이블이 제거됨.

원래 계산 방법을 사용하면 기간은 5시간입니다(9:00~14:00). 누적 레이블 이벤트 기간 계산을 활성화하면 기간은 3시간입니다(9:00~10:00 및 12:00~14:00).

> [!note]
> GitLab 버전을 16.10(또는 그 이상)으로 업그레이드하면 기존 레이블 기반 가치 흐름 분석 스테이지가 배경 집계 프로세스를 사용하여 자동으로 재집계됩니다.

### 커스텀 가치 흐름을 위한 레이블 기반 스테이지 {#label-based-stages-for-custom-value-streams}

복잡한 워크플로우를 측정하려면 [범위 지정 레이블](../../project/labels.md#scoped-labels)을 사용할 수 있습니다. 예를 들어 스테이징 환경에서 프로덕션으로의 배포 시간을 측정하려면 다음 레이블을 사용할 수 있습니다:

- 코드가 스테이징에 배포되면 `workflow::staging` 레이블이 병합 요청에 추가됩니다.
- 코드가 프로덕션에 배포되면 `workflow::production` 레이블이 병합 요청에 추가됩니다.

#### 웹후크를 통한 자동 데이터 레이블링 {#automatic-data-labeling-with-webhooks}

가치 흐름 분석은 백엔드 프로세스를 사용하여 스테이지 수준 데이터를 수집 및 집계하므로 많은 수의 이슈 및 병합 요청이 있는 대규모 그룹으로 확장할 수 있습니다. 이 프로세스로 인해 작업이 수행될 때(예: 이슈 종료) 데이터가 가치 흐름 분석 페이지에 표시될 때까지 약간의 지연이 있을 수 있습니다.

데이터를 처리하고 결과를 표시하는 데 최대 10분이 걸릴 수 있습니다. 데이터 수집이 다음 경우 10분 이상 걸릴 수 있습니다:

- 처음으로 가치 흐름 분석을 보고 아직 가치 흐름을 생성하지 않은 경우입니다.
- 그룹 계층이 재정렬된 경우입니다.
- 이슈 및 병합 요청에 대한 대량 업데이트가 있는 경우입니다.

데이터가 가장 최근에 업데이트된 시점을 보려면 **편집** 옆의 오른쪽 모서리에서 **최근 업데이트** 배지 위에 마우스를 올려놓으세요.

## 가치 흐름 분석 보기 {#view-value-stream-analytics}

사전 요구 사항:

- 보고자, 개발자, 유지 관리자 또는 소유자 역할이 있어야 합니다.
- 커스텀 가치 흐름을 생성해야 합니다. 가치 흐름 분석은 그룹 또는 프로젝트에 대해 생성된 커스텀 가치 흐름만 표시합니다.

그룹 또는 프로젝트에 대한 가치 흐름 분석을 보려면:

1. 상단 표시줄에서 **검색 또는 이동**을 선택하고 프로젝트 또는 그룹을 찾습니다.
1. 왼쪽 사이드바에서 **분석** > **가치 흐름 분석**을 선택합니다.
1. **필터 결과** 텍스트 상자 아래의 스테이지를 선택하여 특정 스테이지에 대한 측정항목을 봅니다.
1. 선택 사항. 결과를 필터링합니다:
   1. **필터 결과** 텍스트 상자를 선택합니다.
   1. 매개 변수를 선택합니다.
   1. 값을 선택하거나 텍스트를 입력하여 결과를 정제합니다.
   1. 특정 날짜 범위에 대한 측정항목을 보려면 드롭다운 목록에서 미리 정의된 날짜 범위 또는 **커스텀** 옵션을 선택합니다. **커스텀** 옵션을 선택하면:

      - **시작** 필드에서 시작 날짜를 선택합니다.
      - **종료** 필드에서 종료 날짜를 선택합니다.

      차트 및 목록은 날짜 범위 동안 생성된 워크플로우 항목을 표시합니다.
1. 선택 사항. 오름차순 또는 내림차순으로 결과를 정렬합니다:
   - 가장 최근 또는 가장 오래된 워크플로우 항목으로 정렬하려면 **최근 이벤트** 헤더를 선택합니다.
   - 각 스테이지에서 가장 많거나 가장 적은 시간 소비 양으로 정렬하려면 **기간** 헤더를 선택합니다.

워크플로우 항목 테이블 헤더 옆의 배지는 선택한 스테이지 동안 완료된 워크플로우 항목의 수를 나타냅니다.

테이블은 선택한 스테이지의 관련 워크플로우 항목 목록을 표시합니다. 선택한 스테이지에 따라 다음을 선택할 수 있습니다:

- 이슈
- 병합 요청

> [!note]
> 각 미리 정의된 날짜 범위의 종료 날짜는 현재 날이며 선택한 일수에 포함됩니다. 예를 들어 `Last 30 days`의 시작 날짜는 현재 날로부터 29일 이전이며 총 30일입니다.

   - **시작 이벤트** 및 **중지 이벤트**를 선택합니다.

1. 스테이지를 다시 정렬하려면 위 또는 아래 화살표를 선택합니다.
1. **새 가치 흐름**을 선택합니다.

## 가치 흐름 편집 {#edit-a-value-stream}

{{< details >}}

- 티어: Premium, Ultimate
- 제공 서비스: GitLab.com, GitLab Self-Managed, GitLab Dedicated

{{< /details >}}

{{< history >}}

- **가치 흐름 편집**이(가) GitLab 16.10에서 [대화상자에서 페이지로 변경](https://gitlab.com/gitlab-org/gitlab/-/issues/381002)되었으며 [기능 플래그](../../../administration/feature_flags/_index.md)는 `vsa_standalone_settings_page`로 명명되었습니다. 기본적으로 비활성화되었습니다.
- [일반적으로 사용 가능](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/171856) (GitLab 17.7) 기능 플래그 `vsa_standalone_settings_page`이 제거되었습니다.

{{< /history >}}

가치 흐름을 생성한 후 목적에 맞게 커스터마이즈할 수 있습니다. 가치 흐름을 편집하려면:

1. 상단 표시줄에서 **검색 또는 이동**을 선택하고 프로젝트 또는 그룹을 찾습니다.
1. 왼쪽 사이드바에서 **분석** > **가치 흐름 분석**을 선택합니다.
1. 가치 흐름 드롭다운 목록에서 편집할 가치 흐름을 선택합니다.
1. 가치 흐름 드롭다운 목록 옆에서 **편집**을 선택합니다.
1. 선택 사항: 
   - 가치 흐름의 이름을 바꿉니다.
   - 기본 스테이지를 숨기거나 다시 정렬합니다.
   - 기존 커스텀 스테이지를 제거합니다.
   - 새 스테이지를 추가하려면 **스테이지 추가**를 선택합니다.
   - 스테이지의 시작 및 종료 이벤트를 선택합니다.
1. 선택 사항. 수정 사항을 취소하려면 **가치 흐름 기본값 복원**을 선택합니다.
1. **가치 흐름 저장**을 선택합니다.

## 가치 흐름 삭제 {#delete-a-value-stream}

{{< details >}}

- 티어: Premium, Ultimate
- 제공 서비스: GitLab.com, GitLab Self-Managed, GitLab Dedicated

{{< /details >}}

커스텀 가치 흐름을 삭제하려면:

1. 상단 표시줄에서 **검색 또는 이동**을 선택하고 프로젝트 또는 그룹을 찾습니다.
1. 왼쪽 사이드바에서 **분석** > **가치 흐름 분석**을 선택합니다.
1. 가치 흐름 드롭다운 목록에서 삭제할 가치 흐름을 선택한 다음 **삭제(가치 흐름 이름)**를 선택합니다.
1. 확인하려면 **삭제**를 선택합니다.

## 사이클 완료 일수 보기 {#view-number-of-days-for-a-cycle-to-complete}

{{< details >}}

- 티어: Premium, Ultimate
- 제공 서비스: GitLab.com, GitLab Self-Managed, GitLab Dedicated

{{< /details >}}

**총 시간 차트**는 개발 사이클을 완료하는 데 걸리는 평균 일 수를 보여줍니다. 차트는 마지막 500개 워크플로우 항목의 데이터를 표시합니다.

1. 상단 표시줄에서 **검색 또는 이동**을 선택하고 프로젝트 또는 그룹을 찾습니다.
1. 왼쪽 사이드바에서 **분석** > **가치 흐름 분석**을 선택합니다.
1. **필터 결과** 상자 위에서 스테이지를 선택합니다:
   - 모든 스테이지의 사이클 타임에 대한 요약을 보려면 **개요**를 선택합니다.
   - 특정 스테이지의 사이클 타임을 보려면 스테이지를 선택합니다.
1. 선택 사항. 결과를 필터링합니다:
   1. **필터 결과** 텍스트 상자를 선택합니다.
   1. 매개 변수를 선택합니다.
   1. 값을 선택하거나 텍스트를 입력하여 결과를 정제합니다.
   1. 날짜 범위를 조정하려면:
      - **시작** 필드에서 시작 날짜를 선택합니다.
      - **종료** 필드에서 종료 날짜를 선택합니다.

## 업그레이드 후 데이터 재집계 {#reaggregate-data-after-upgrade}

{{< details >}}

- 제공 서비스: GitLab Self-Managed

{{< /details >}}

특히 여러 부 버전을 건너뛴 경우 대규모 인스턴스에서 GitLab 버전을 업그레이드할 때 배경 집계 프로세스가 더 오래 걸릴 수 있습니다. 이러한 지연으로 인해 가치 흐름 분석 페이지에서 오래된 데이터가 표시될 수 있습니다. 집계 프로세스 속도를 높이고 오래된 데이터를 피하려면 [Rails 콘솔](../../../administration/operations/rails_console.md#starting-a-rails-console-session)에서 주어진 그룹에 대한 동기 집계 코드 조각을 호출할 수 있습니다:

```ruby
group = Group.find(-1) # put your group id here
group_to_aggregate = group.root_ancestor

loop do
  cursor = {}
  context = Analytics::CycleAnalytics::AggregationContext.new(cursor: cursor)
  service_response = Analytics::CycleAnalytics::DataLoaderService.new(group: group_to_aggregate, model: Issue, context: context).execute

  if service_response.success? && service_response.payload[:reason] == :limit_reached
    cursor = service_response.payload[:context].cursor
  elsif service_response.success?
    puts "finished"
    break
  else
    puts "failed"
    break
  end
end

loop do
  cursor = {}
  context = Analytics::CycleAnalytics::AggregationContext.new(cursor: cursor)
  service_response = Analytics::CycleAnalytics::DataLoaderService.new(group: group_to_aggregate, model: MergeRequest, context: context).execute

  if service_response.success? && service_response.payload[:reason] == :limit_reached
    cursor = service_response.payload[:context].cursor
  elsif service_response.success?
    puts "finished"
    break
  else
    puts "failed"
    break
  end
end
```

## 기능 가용성 {#feature-availability}

가치 흐름 분석은 프로젝트 및 그룹에 대한 기능을 제공하며 티어에 따라 가용성이 다릅니다.

- Free 티어에서 가치 흐름 분석은 데이터를 집계하지 않습니다. 날짜 범위 필터가 이슈 및 병합 요청의 생성 날짜에 적용되는 데이터베이스를 직접 쿼리합니다. 미리 정의된 기본 스테이지로 가치 흐름 분석을 볼 수 있습니다.

## 문제 해결 {#troubleshooting}

### Sidekiq `cronjob:analytics_cycle_analytics`의 100% CPU 사용률 {#100-cpu-utilization-by-sidekiq-cronjobanalytics_cycle_analytics}

가치 흐름 분석 배경 작업이 CPU 리소스를 독점하여 성능에 강하게 영향을 미칠 수 있습니다.

이 상황에서 복구하려면:

1. [Rails 콘솔](../../../administration/operations/rails_console.md)에서 모든 프로젝트의 기능을 비활성화하고 기존 작업을 제거합니다:

   ```ruby
   Project.find_each do |p|
     p.analytics_access_level='disabled';
     p.save!
   end

   Analytics::CycleAnalytics::GroupStage.delete_all
   Analytics::CycleAnalytics::Aggregation.delete_all
   ```

1. [Sidekiq 라우팅](../../../administration/sidekiq/processing_specific_job_classes.md)을 구성합니다. 예를 들어 단일 `feature_category=value_stream_management` 및 여러 `feature_category!=value_stream_management` 항목입니다. [Enterprise Edition 목록](../../../administration/sidekiq/processing_specific_job_classes.md#list-of-available-job-classes)에서 다른 관련 큐 메타데이터를 찾습니다.
1. 프로젝트 하나씩 가치 흐름 분석을 활성화합니다. 성능 요구사항에 따라 Sidekiq 라우팅을 추가로 조정해야 할 수 있습니다.
