보호 규칙은 브랜치에 대한 접근을 제어하고 여러 규칙이 동일한 브랜치에 적용될 때 어떤 일이 발생하는지 결정합니다. 리포지토리 브랜치에 대한 올바른 보안 조치를 구현하는 데 도움이 됩니다. 이러한 규칙은 다음을 포함합니다:

- 권한 수준, 우선 순위 및 규칙 충돌.
- 여러 일치하는 규칙에 대한 강제 푸시 권한.
- 코드 소유자 승인.
- 그룹과 프로젝트 간의 보호 설정.

## 규칙 동작 {#rule-behaviors}

브랜치가 여러 보호 규칙과 일치할 때 이러한 동작이 적용됩니다:

- 그룹 규칙은 그룹의 모든 프로젝트에 적용되며 프로젝트 설정에서 수정할 수 없습니다. 자세한 내용은 [그룹 및 프로젝트 전체의 규칙](#rules-across-groups-and-projects)을 참조하세요.
- 브랜치가 여러 규칙과 일치할 때 가장 허용적인 규칙이 적용됩니다. 하지만 [코드 소유자 승인](#code-owner-approval)은 가장 제한적인 규칙을 사용합니다.
- `main`과 같은 정확한 브랜치 이름은 `m*`과 같은 와일드카드 패턴을 재정의하지 않습니다.

## 푸시 및 머지 권한 {#push-and-merge-permissions}

브랜치가 보호되면 기본 동작이 다음과 같은 제한을 적용합니다:

| 작업                   | 이를 수행할 수 있는 사람 |
|:-------------------------|:--------------|
| 브랜치 보호         | 유지관리자 또는 소유자 역할을 가진 사용자입니다. |
| 브랜치에 푸시       | **허용됨** 권한을 가진 모든 사용자입니다. (1) |
| 브랜치에 강제 푸시 | 아무도 없음.       |
| 브랜치 삭제        | 아무도 없음. (2)   |

1. 개발자 역할을 가진 사용자는 그룹에서 프로젝트를 만들 수 있지만 처음에는 [기본 브랜치](default.md)에 푸시하지 못할 수 있습니다.
1. 아무도 Git 명령을 사용하여 보호된 브랜치를 삭제할 수 없습니다. 하지만 최소한 유지관리자 역할을 가진 사용자는 UI 또는 API에서 [보호된 브랜치를 삭제](protected.md#delete-protected-branches)할 수 있습니다.

이러한 권한을 구성할 때 역할을 선택하면 해당 역할과 모든 상위 역할을 가진 사용자에게 접근 권한을 부여합니다. 예를 들어:

- **유지관리자**를 선택하면 유지관리자 및 소유자 역할을 가진 사용자에게 접근 권한을 부여합니다.
- **개발자 + 유지관리자**를 선택하면 개발자, 유지관리자 및 소유자 역할을 가진 사용자에게 접근 권한을 부여합니다.

이 동작은 더 높은 권한을 가진 사용자가 더 낮은 권한을 가진 사용자에게 제공되는 접근 권한을 유지하도록 보장합니다.

## 강제 푸시 권한 {#force-push-permissions}

강제 푸시 권한은 동일한 가장 허용적인 규칙 적용 논리를 따릅니다. 예를 들어 [와일드카드](protected.md#use-wildcard-rules)를 포함하는 이러한 규칙을 고려하세요:

| 브랜치 이름 패턴 | 강제 푸시 허용 |
|---------------------|------------------|
| `v1.x`              | 예              |
| `v1.*`              | 아니요               |
| `v*`                | 아니요               |

`v1.x` 이름의 브랜치는 세 가지 브랜치 이름 패턴 모두와 일치합니다: `v1.x`, `v1.*`, `v*`. 가장 허용적인 옵션이 동작을 결정하므로 브랜치 `v1.x`의 결과 권한은 다음과 같습니다:

- **강제 푸시 허용**: 세 가지 설정 중 `Yes`은 가장 허용적이며 결과적으로 브랜치 동작을 제어합니다. 브랜치가 `v1.x`과 `v*`(각각 더 엄격한 권한이 있는)과도 일치했지만 이 브랜치로 푸시할 수 있는 모든 사용자는 강제 푸시도 할 수 있습니다.

## 코드 소유자 승인 {#code-owner-approval}

{{< details >}}

- 티어: Premium, Ultimate
- 제공 서비스: GitLab.com, GitLab Self-Managed, GitLab Dedicated

{{< /details >}}

푸시 및 머지 권한 및 강제 푸시 권한과 달리 코드 소유자 승인은 가장 제한적인 규칙을 사용합니다. 브랜치가 여러 규칙에 의해 보호되는 경우 적용 가능한 규칙 중 하나라도 **코드 소유자 승인 필요**를 활성화하면 코드 소유자 승인이 필요합니다. 자세한 내용은 [코드 소유자 승인 필요](protected.md#require-code-owner-approval)를 참조하세요.

예를 들어 이러한 규칙을 고려하세요:

| 브랜치 이름 패턴 | 코드 소유자 승인 필요 |
|---------------------|------------------------------|
| `v1.x`              | 예                          |
| `v1.*`              | 아니요                           |
| `v*`                | 아니요                           |

`v1.x` 이름의 브랜치는 세 가지 브랜치 이름 패턴 모두와 일치합니다: `v1.x`, `v1.*`, `v*`. 최소한 하나의 규칙(`v1.x`)이 코드 소유자 승인을 필요로 하므로 이 브랜치에 대한 모든 머지 리퀘스트는 병합되기 전에 코드 소유자의 승인이 필요합니다.

## 그룹 및 프로젝트 간 규칙 {#rules-across-groups-and-projects}

브랜치 보호 규칙은 그룹과 프로젝트 모두에서 설정할 수 있습니다:

- 그룹 규칙은 그룹의 모든 프로젝트에 적용되며 프로젝트 설정에서 수정할 수 없습니다.
- 프로젝트 규칙은 설정된 프로젝트에만 적용됩니다.

그룹과 프로젝트 규칙이 모두 브랜치와 일치할 때 GitLab은 모든 일치하는 규칙을 함께 평가합니다:

- 대부분의 설정에서 가장 허용적인 규칙이 적용됩니다.
- [코드 소유자 승인](#code-owner-approval)의 경우 가장 제한적인 규칙이 적용됩니다.

프로젝트 설정에서 그룹 규칙을 편집하거나 제거할 수 없지만 동일한 브랜치에 대해 프로젝트 규칙을 추가할 수 있습니다. 결합된 평가는 그룹 규칙만으로는 불가능한 더 허용적인 동작을 초래할 수 있습니다.

예를 들어:

- `main`에 대한 그룹 규칙이 강제 푸시를 거부합니다.
- 프로젝트 유지관리자가 강제 푸시를 허용하는 `main`에 대한 프로젝트 규칙을 추가합니다.
- 두 규칙 모두 함께 평가됩니다. 가장 허용적인 규칙이 적용되므로 해당 프로젝트의 `main` 브랜치에서 강제 푸시가 허용됩니다.

## 여러 브랜치 규칙 예제 {#multiple-branch-rule-examples}

다음 예제는 서로 다른 규칙이 브랜치 보호에 어떻게 영향을 미칠 수 있는지 보여줍니다.

### 머지 허용 {#allowed-to-merge}

정확한 브랜치 이름이 더 허용적인 와일드카드 패턴을 재정의하지 않는 방법의 예입니다.

| 브랜치 패턴 | 머지 허용          |
|----------------|---------------------------|
| `release-v1.0` | 아무도 없음                    |
| `release*`     | Maintainer                |
| `*`            | 개발자 + 유지관리자    |

- 브랜치 `release-v1.0`은 세 가지 패턴 모두와 일치합니다. 가장 허용적인 규칙이 적용됩니다:
  - **머지 허용**: 개발자 + 유지관리자는 (`*` 규칙에서) 머지할 수 있습니다.

### 푸시와 머지가 허용됨 {#allowed-to-push-and-merge}

여러 브랜치 규칙이 서로 다른 브랜치 이름에 어떻게 적용되는지의 예입니다.

| 브랜치 패턴 | 머지 허용       | 푸시와 머지가 허용됨 |
|----------------|------------------------|---------------------------|
| `main`         | Maintainer             | 아무도 없음                    |
| `m*`           | 개발자 + 유지관리자 | 개발자 + 유지관리자    |
| `r*`           | 아무도 없음                 | 아무도 없음                    |

- 브랜치 `main`은 두 가지 패턴(`main`과 `m*`)과 일치합니다. 가장 허용적인 규칙이 적용됩니다:
  - **머지 허용**: 개발자 + 유지관리자는 (`m*` 규칙에서) 머지할 수 있습니다.
  - **푸시와 머지가 허용됨**: 개발자 + 유지관리자는 (`m*` 규칙에서) 푸시할 수 있습니다.
- 브랜치 `release-v1.0`은 하나의 패턴과 일치합니다:
  - **머지 허용**: 아무도 (`r*` 규칙에서) 머지할 수 없습니다.
  - **푸시와 머지가 허용됨**: 아무도 (`r*` 규칙에서) 푸시할 수 없습니다.

### 코드 소유자 요구 사항 {#code-owner-requirements}

코드 소유자 승인은 다른 브랜치 보호 설정과 다르게 작동합니다. 여러 규칙이 일치할 때 가장 허용적인 규칙 대신 가장 제한적인 규칙이 적용됩니다.

| 브랜치 패턴 | 코드 소유자 승인 필요 |
|----------------|------------------------------|
| `production`   | 예                          |
| `prod*`        | 아니요                           |
| `p*`           | 예                          |

- 브랜치 `production`은 세 가지 패턴 모두와 일치합니다. 가장 제한적인 규칙이 적용됩니다:
  - **코드 소유자 승인**: (`production`과 `p*` 규칙에서) 필수입니다.
- 브랜치 `product-v1.0`은 두 가지 패턴(`prod*`과 `p*`)과 일치합니다. 가장 제한적인 규칙이 적용됩니다:
  - **코드 소유자 승인**: (`p*` 규칙에서) 필수입니다.

### 엄격한 보호 보장 {#ensure-strict-protection}

더 허용적인 패턴에 의해 재정의될 수 없는 엄격한 보호를 보장하려면 모든 일치하는 패턴을 동일한 제한적 설정으로 구성하세요.

| 브랜치 패턴 | 머지 허용 | 푸시와 머지가 허용됨 |
|----------------|------------------|---------------------------|
| `production`   | Maintainer       | 아무도 없음                    |
| `prod*`        | Maintainer       | 아무도 없음                    |
| `p*`           | Maintainer       | 아무도 없음                    |
| `*`            | Maintainer       | 아무도 없음                    |

이제 브랜치 `production`은 모든 일치하는 규칙이 **아무도 없음** 푸시할 수 없음을 지정하기 때문에 제한적 푸시 권한을 갖습니다.
