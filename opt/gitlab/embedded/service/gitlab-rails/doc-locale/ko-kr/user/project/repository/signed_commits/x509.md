[X.509](https://en.wikipedia.org/wiki/X.509)는 공개 또는 개인 공개 키 인프라(PKI)에서 발급한 공개 키 인증서의 표준 형식입니다. 개인 X.509 인증서는 S/MIME(Secure/Multipurpose Internet Mail Extensions)과 같은 인증 또는 서명 목적으로 사용됩니다. 그러나 Git도 [GPG(GnuPG 또는 GNU Privacy Guard)](gpg.md)와 유사한 방식으로 X.509 인증서를 사용한 커밋 및 태그 서명을 지원합니다. 주요 차이점은 GitLab이 개발자의 서명을 신뢰할 수 있는지 여부를 결정하는 방식입니다:

- X.509의 경우 루트 인증 기관이 GitLab 신뢰 저장소에 추가됩니다. (신뢰 저장소는 신뢰할 수 있는 보안 인증서의 리포지토리입니다.) 서명에 포함된 필수 중간 인증서와 함께, 개발자의 인증서를 신뢰할 수 있는 루트 인증서로 연결할 수 있습니다.
- GPG의 경우 개발자는 [GPG 키를 추가](gpg.md#add-a-gpg-key-to-your-account)하여 계정에 연결합니다.

GitLab은 자체 인증서 저장소를 사용하며 따라서 [신뢰 체인](https://www.ssl.com/article/what-is-a-certificate-authority-ca/)을 정의합니다. GitLab에서 커밋 또는 태그를 확인하려면:

- 서명 인증서 이메일은 GitLab의 확인된 이메일 주소와 일치해야 합니다.
- GitLab 인스턴스는 서명의 인증서에서 GitLab 인증서 저장소의 신뢰할 수 있는 인증서로의 완전한 신뢰 체인이 필요합니다. 이 체인에는 서명에 제공된 중간 인증서가 포함될 수 있습니다. Certificate Authority 루트 인증서와 같은 인증서를 [GitLab 인증서 저장소](https://docs.gitlab.com/omnibus/settings/ssl/#install-custom-public-certificates)에 추가해야 할 수도 있습니다.
- 서명 시간은 보통 최대 3년인 [인증서 유효성](https://www.rfc-editor.org/rfc/rfc5280.html#section-4.1.2.5)의 시간 범위 내에 있어야 합니다.
- 서명 시간은 커밋 시간과 같거나 그보다 나중이어야 합니다.

> [!note]
> 신뢰 체인의 루트 CA 또는 중간 인증서가 만료되고 갱신되면, [다시 확인](#re-verify-commits)할 때까지 커밋이 일시적으로 "검증되지 않음"으로 표시될 수 있습니다.

커밋의 상태가 이미 결정되어 데이터베이스에 저장된 경우 Rake 작업을 사용하여 [상태를 다시 확인](../../../../administration/raketasks/x509_signatures.md)합니다. GitLab은 백그라운드 워커를 사용하여 매일 인증서 폐지 목록을 확인합니다.

## 알려진 이슈 {#known-issues}

- `authorityKeyIdentifier`, `subjectKeyIdentifier`, 및 `crlDistributionPoints`이 없는 인증서는 **미인증**으로 표시됩니다. [RFC 5280](https://www.rfc-editor.org/info/rfc5280/)에 부합하는 PKI의 인증서를 사용하기를 권장합니다.
- **검증됨** 배지는 [사용자 지정 인증 기관(CA) 업로드](https://docs.gitlab.com/omnibus/settings/ssl/#install-custom-public-certificates)가 GitLab Self-Managed에만 제공되므로 GitLab.com 제공 서비스에 표시되지 않습니다.
- 필수 Key Usage (KU) `Digital Signature` 외에 Extended Key Usage (EKU) 섹션에서 값을 설정하면 커밋이 **미인증**으로 표시될 수 있습니다. 이를 해결하려면 `emailProtection`를 EKU 목록에 추가합니다. RFC 5280은 이 제한을 지정합니다.

  진단하려면 [S/MIME 검증 및 OpenSSL](#smime-verification-with-openssl)을 따릅니다.
- GitLab 16.2 및 이전 버전에서 서명 인증서의 Subject Alternative Name 목록에 둘 이상의 이메일이 있는 경우, [처음 이메일만 커밋 확인에 사용됩니다](https://gitlab.com/gitlab-org/gitlab/-/issues/336677).

## 서명된 커밋에 대해 구성 {#configure-for-signed-commits}

커밋, 태그 또는 둘 다에 서명하려면 다음을 수행해야 합니다:

1. [X.509 키 쌍 획득](#obtain-an-x509-key-pair)
1. [X.509 인증서를 Git과 연결](#associate-your-x509-certificate-with-git)
1. [커밋 서명 및 확인](#sign-and-verify-commits)
1. [태그 서명 및 확인](#sign-and-verify-tags)

### X.509 키 쌍 획득 {#obtain-an-x509-key-pair}

조직에 공개 키 인프라(PKI)가 있는 경우 해당 PKI는 S/MIME 키를 제공합니다. PKI에서 S/MIME 키 쌍이 없으면 직접 자체 서명된 쌍을 만들거나 쌍을 구매합니다.

### X.509 인증서를 Git과 연결 {#associate-your-x509-certificate-with-git}

X.509 서명을 활용하려면 Git 2.19.0 이상이 필요합니다. `git --version` 명령으로 Git 버전을 확인할 수 있습니다.

올바른 버전이 있으면 Git 구성으로 진행할 수 있습니다.

{{< tabs >}}

{{< tab title="Linux" >}}

Git을 구성하여 서명할 키를 사용합니다:

```shell
signingkey=$( gpgsm --list-secret-keys | egrep '(key usage|ID)' | grep -B 1 digitalSignature | awk '/ID/ {print $2}' )
git config --global user.signingkey $signingkey
git config --global gpg.format x509
```

{{< / tab >}}

{{< tab title="Windows 및 macOS" >}}

Windows 또는 macOS를 구성하려면:

1. [S/MIME Sign](https://github.com/github/smimesign)을 다음 중 하나로 설치합니다:
   - 설치 프로그램을 다운로드합니다.
   - macOS에서 `brew install smimesign`을 실행합니다.
1. `smimesign --list-keys`을 실행하여 인증서의 ID를 가져옵니다.
1. `git config --global user.signingkey <ID>`을 실행하여 서명 키를 설정하고, `<ID>`를 인증서 ID로 바꿉니다.
1. 다음 명령으로 X.509를 구성합니다:

   ```shell
   git config --global gpg.x509.program smimesign
   git config --global gpg.format x509
   ```

{{< /tab >}}

{{< /tabs >}}

### 커밋 서명 및 확인 {#sign-and-verify-commits}

[X.509 인증서를 Git과 연결](#associate-your-x509-certificate-with-git)한 후 커밋에 서명할 수 있습니다:

1. Git 커밋을 생성할 때 `-S` 플래그를 추가합니다:

   ```shell
   git commit -S -m "feat: x509 signed commits"
   ```

1. GitLab으로 푸시하고 `--show-signature` 플래그로 커밋이 확인되었는지 확인합니다:

   ```shell
   git log --show-signature
   ```

1. *매번 커밋할 때 `-S` 플래그를 입력하고 싶지 않으면* Git이 매번 커밋에 서명하도록 이 명령을 실행합니다:

   ```shell
   git config --global commit.gpgsign true
   ```

### 태그에 서명 및 검증 {#sign-and-verify-tags}

[X.509 인증서를 Git과 연결](#associate-your-x509-certificate-with-git)한 후 태그에 서명을 시작할 수 있습니다:

1. Git 태그를 생성할 때 `-s` 플래그를 추가합니다:

   ```shell
   git tag -s v1.1.1 -m "My signed tag"
   ```

1. GitLab으로 푸시하고 다음 명령으로 태그가 서명되었는지 확인합니다:

   ```shell
   git tag --verify v1.1.1
   ```

1. *매번 태그할 때 `-s` 플래그를 입력하고 싶지 않으면* Git이 매번 태그에 서명하도록 이 명령을 실행합니다:

   ```shell
   git config --global tag.gpgsign true
   ```

## 문제 해결 {#troubleshooting}

관리자 액세스 권한이 없는 커밋터는 [서명된 커밋의 확인 문제](_index.md#fix-verification-problems-with-signed-commits) 목록을 검토하여 가능한 해결책을 찾으세요. 이 페이지의 다른 문제 해결 제안에는 관리자 액세스 권한이 필요합니다.

### 커밋 다시 확인 {#re-verify-commits}

GitLab은 확인된 커밋의 상태를 데이터베이스에 저장합니다. 다음 후 커밋을 다시 확인할 수 있습니다:

- 루트 CA 또는 중간 인증서를 갱신합니다.
- 인증서 저장소에 변경 사항을 적용합니다.

커밋을 다시 확인하려면:

1. 루트 CA 및 모든 중간 인증서가 GitLab 인증서 저장소에 있는지 확인합니다.
1. [`update_signatures` Rake 작업](../../../../administration/raketasks/x509_signatures.md)을 실행하여 이전에 확인된 커밋의 상태를 확인하고 업데이트합니다.

### 주요 확인 검사 {#main-verification-checks}

코드는 [다음 주요 검사](https://gitlab.com/gitlab-org/gitlab/-/blob/v14.1.0-ee/lib/gitlab/x509/signature.rb#L33)를 수행하며, 모두 `verified`를 반환해야 합니다:

- `x509_certificate.nil?`은 false여야 합니다.
- `x509_certificate.revoked?`은 false여야 합니다.
- `verified_signature`은 true여야 합니다.
- `user.nil?`은 false여야 합니다.
- `user.verified_emails.include?(@email)`은 true여야 합니다.
- `certificate_email == @email`은 true여야 합니다.

커밋이 `Unverified`로 표시되는 이유를 조사하려면:

1. [Rails 콘솔 시작](../../../../administration/operations/rails_console.md#starting-a-rails-console-session):

   ```shell
   sudo gitlab-rails console
   ```

1. 조사 중인 프로젝트(경로 또는 ID로) 및 전체 커밋 SHA를 식별합니다. 이 정보를 사용하여 `signature`을 생성하여 다른 검사를 실행합니다:

   ```ruby
   project = Project.find_by_full_path('group/subgroup/project')
   project = Project.find_by_id('121')
   commit = project.repository.commit_by(oid: '87fdbd0f9382781442053b0b76da729344e37653')
   signedcommit=Gitlab::X509::Commit.new(commit)
   signature=Gitlab::X509::Signature.new(signedcommit.signature_text, signedcommit.signed_text, commit.committer_email, commit.created_at, commit.project)
   ```

   검사를 통해 실행된 식별된 문제를 해결하기 위해 변경 사항을 적용하면 Rails 콘솔을 다시 시작하고 처음부터 검사를 다시 실행합니다.

1. 커밋의 인증서를 확인합니다:

   ```ruby
   signature.x509_certificate.nil?
   signature.x509_certificate.revoked?
   ```

   두 검사 모두 `false`을 반환해야 합니다:

   ```ruby
   > signature.x509_certificate.nil?
   => false
   > signature.x509_certificate.revoked?
   => false
   ```

1. 서명에 대한 암호화 검사를 실행합니다. 코드는 `true`을 반환해야 합니다:

   ```ruby
   signature.verified_signature
   ```

   `false`을 반환하면 [이 검사를 추가로 조사](#cryptographic-verification-checks)합니다.

1. 커밋 및 서명의 이메일 주소가 일치하는지 확인합니다:

   - Rails 콘솔은 비교 중인 이메일 주소를 표시합니다.
   - 최종 명령은 `true`을 반환해야 합니다:

   ```ruby
   sigemail=signature.__send__:certificate_email
   commitemail=commit.committer_email
   sigemail == commitemail
   ```

   GitLab 16.2 및 이전 버전에서 [처음 이메일만](https://gitlab.com/gitlab-org/gitlab/-/issues/336677) `Subject Alternative Name` 목록에서 비교됩니다. `Subject Alternative Name` 목록을 표시하려면 다음을 실행합니다:

   ```ruby
   signature.__send__ :get_certificate_extension,'subjectAltName'
   ```

   개발자의 이메일 주소가 목록의 첫 번째가 아니면 이 검사가 실패하고 커밋이 `unverified`으로 표시됩니다.

1. 커밋의 이메일 주소는 GitLab의 계정과 연결되어야 합니다. 이 검사는 `false`을 반환해야 합니다:

   ```ruby
   signature.user.nil?
   ```

1. 이메일 주소가 GitLab의 사용자와 연결되어 있는지 확인합니다. 이 검사는 `#<User id:1234 @user_handle>`과 같은 사용자를 반환해야 합니다:

   ```ruby
   User.find_by_any_email(commit.committer_email)
   ```

   `nil`을 반환하면 이메일 주소가 사용자와 연결되지 않으며 검사가 실패합니다.

1. 개발자의 이메일 주소가 확인되었는지 확인합니다. 이 검사는 true를 반환해야 합니다:

   ```ruby
   signature.user.verified_emails.include?(commit.committer_email)
   ```

   이전 검사에서 `nil`을 반환했으면 이 명령은 오류를 표시합니다:

   ```plaintext
   NoMethodError (undefined method `verified_emails' for nil:NilClass)
   ```

1. 확인 상태는 데이터베이스에 저장됩니다. 데이터베이스 레코드를 표시하려면:

   ```ruby
   pp CommitSignatures::X509CommitSignature.by_commit_sha(commit.sha);nil
   ```

   이전의 모든 검사에서 올바른 값을 반환한 경우:

   - `verification_status: "unverified"`는 데이터베이스 레코드를 업데이트해야 함을 나타냅니다. [Rake 작업 사용](#re-verify-commits)

   - `[]`는 데이터베이스에 아직 레코드가 없음을 나타냅니다. GitLab의 커밋을 찾아 서명을 확인하고 결과를 저장합니다.

#### 암호화 확인 검사 {#cryptographic-verification-checks}

GitLab이 `verified_signature`이 `false`임을 결정하면 Rails 콘솔에서 이유를 조사합니다. 이 검사에는 `signature`이 존재해야 합니다. 이전 [주요 확인 검사](#main-verification-checks)의 `signature` 단계를 참조합니다.

1. 발급자를 확인하지 않고 서명을 확인하고 `true`을 반환합니다:

   ```ruby
   signature.__send__ :valid_signature?
   ```

1. 서명 시간 및 날짜를 확인합니다. 이 검사는 `true`을 반환해야 합니다:

   ```ruby
   signature.__send__ :valid_signing_time?
   ```

   - 코드는 코드 서명 인증서가 만료되도록 허용합니다.
   - 커밋은 인증서의 유효 기간 동안 서명해야 하며 커밋의 날짜 스탬프와 같거나 그 이후여야 합니다. 커밋 시간과 `not_before`, `not_after`를 포함한 인증서 세부 정보를 표시합니다:

     ```ruby
     commit.created_at
     pp signature.__send__ :cert; nil
     ```

1. TLS 신뢰를 설정할 수 있는지 포함하여 서명을 확인합니다. 이 검사는 `true`을 반환해야 합니다:

   ```ruby
   signature.__send__(:p7).verify([], signature.__send__(:cert_store), signature.__send__(:signed_text))
   ```

   1. 실패하면 신뢰를 설정하기 위해 필요한 누락된 인증서를 [GitLab 인증서 저장소](https://docs.gitlab.com/omnibus/settings/ssl/#install-custom-public-certificates)에 추가합니다.

   1. 더 많은 인증서를 추가한 후 (이 문제 해결 단계를 통과하면) Rake 작업을 실행하여 [커밋을 다시 확인](#re-verify-commits)합니다.

   1. Rails 콘솔에서 추가 인증서를 동적으로 추가하여 이것이 문제를 해결하는지 확인할 수 있습니다.

      1. 수정할 수 있는 `cert_store` 신뢰 저장소로 서명을 다시 테스트합니다. 여전히 `false`로 실패해야 합니다:

         ```ruby
         cert_store = signature.__send__ :cert_store
         signature.__send__(:p7).verify([], cert_store, signature.__send__(:signed_text))
         ```

      1. 추가 인증서를 추가하고 다시 테스트합니다:

         ```ruby
         cert_store.add_file("/etc/ssl/certs/my_new_root_ca.pem")
         signature.__send__(:p7).verify([], cert_store, signature.__send__(:signed_text))
         ```

   1. 서명에 포함된 인증서를 표시합니다:

      ```ruby
      pp signature.__send__(:p7).certificates ; nil
      ```

   1. [명령줄에서 OpenSSL로 추가 조사를 수행할 수 있습니다](#smime-verification-with-openssl).

추가 중간 인증서 및 루트 인증서를 인증서 저장소에 추가합니다. 웹 서버에서 인증서 체인이 구축되는 방식과의 일관성을 위해:

- 커밋에 서명하는 Git 클라이언트는 인증서와 모든 중간 인증서를 서명에 포함해야 합니다.
- GitLab 인증서 저장소는 루트만 포함해야 합니다.

GitLab 신뢰 저장소에서 루트 인증서를 제거하면 (예를 들어 만료될 때) 해당 루트로 다시 연결되는 커밋 서명이 `unverified`으로 표시됩니다.

#### S/MIME 검증 및 OpenSSL {#smime-verification-with-openssl}

서명에 문제가 있거나 TLS 신뢰가 실패하면 명령줄에서 OpenSSL을 사용하여 추가 디버깅을 수행할 수 있습니다.

[Rails 콘솔](../../../../administration/operations/rails_console.md#starting-a-rails-console-session)에서 서명 및 서명된 텍스트를 내보냅니다:

1. [주요 확인 검사](#main-verification-checks)의 초기 두 단계가 `signature`이 설정되도록 필요합니다.
1. OpenSSL은 PKCS7 PEM 형식 데이터가 `BEGIN PKCS7` 및 `END PKCS7`로 제한되도록 하므로 일반적으로 수정해야 합니다:

   ```ruby
   pkcs7_text = signature.signature_text.sub('-----BEGIN SIGNED MESSAGE-----', '-----BEGIN PKCS7-----')
   pkcs7_text = pkcs7_text.sub('-----END SIGNED MESSAGE-----', '-----END PKCS7-----')
   ```

1. 서명 및 서명된 텍스트를 작성합니다:

   ```ruby
   f1=File.new('/tmp/signature_text.pk7.pem','w')
   f1 << pkcs7_text
   f1.close

   f2=File.new('/tmp/signed_text.txt','w')
   f2 << signature.signed_text
   f2.close
   ```

이제 이 데이터를 Linux 명령줄에서 OpenSSL을 사용하여 조사할 수 있습니다:

1. 서명을 포함하는 PKCS #7 파일을 쿼리할 수 있습니다:

   ```shell
   /opt/gitlab/embedded/bin/openssl pkcs7 -inform pem -print_certs \
       -in /tmp/signature_text.pk7.pem -print -noout
   ```

   출력에 최소 하나의 `cert` 섹션이 포함되어야 합니다. 서명자의 인증서입니다.

   출력에 많은 세부 정보가 있습니다. 다음은 존재해야 하는 구조 및 제목의 일부 예입니다:

   ```plaintext
   PKCS7:
     d.sign:
       cert:
           cert_info:
             issuer:
             validity:
               notBefore:
               notAfter:
             subject:
   ```

   개발자의 코드 서명 인증서가 중간 인증 기관에서 발급된 경우 추가 인증서 세부 정보가 있어야 합니다:

   ```plaintext
   PKCS7:
     d.sign:
       cert:
           cert_info:
       cert:
           cert_info:
   ```

1. 서명에서 인증서를 추출합니다:

   ```shell
   /opt/gitlab/embedded/bin/openssl pkcs7 -inform pem -print_certs \
       -in /tmp/signature_text.pk7.pem -out /tmp/signature_cert.pem
   ```

   이 단계가 실패하면 서명에 서명자의 인증서가 없을 수 있습니다.

   - Git 클라이언트에서 이 문제를 해결합니다.
   - 다음 단계는 실패하지만 서명자의 인증서를 GitLab 서버에 복사하면 `-nointern -certfile signerscertificate.pem`을 사용하여 일부 테스트를 수행할 수 있습니다.

1. 추출된 인증서를 사용하여 커밋을 부분적으로 확인합니다:

   ```shell
   /opt/gitlab/embedded/bin/openssl smime -verify -binary -inform pem \
       -in /tmp/signature_text.pk7.pem -content /tmp/signed_text.txt \
       -noverify -certfile /tmp/signature_cert.pem -nointern
   ```

   출력은 일반적으로 다음을 포함합니다:

   - 상위 커밋
   - 커밋의 이름, 이메일 및 타임스탬프
   - 커밋 텍스트
   - `Verification successful` (또는 유사)

   이 검사는 GitLab이 수행하는 검사와 동일하지 않습니다:

   - 서명자의 인증서(`-noverify`)를 확인하지 않습니다
   - 확인은 메시지의 `-nointern`가 아닌 제공된 `-certfile`을 사용하여 수행됩니다

1. 메시지의 인증서를 사용하여 커밋을 부분적으로 확인합니다:

   ```shell
   /opt/gitlab/embedded/bin/openssl smime -verify -binary -inform pem \
       -in /tmp/signature_text.pk7.pem -content /tmp/signed_text.txt \
       -noverify
   ```

   이는 추출된 인증서를 사용하는 이전 단계와 동일한 결과를 얻어야 합니다.

   메시지에 인증서가 없으면 오류에 `signer certificate not found`이 포함됩니다.

1. 커밋을 완전히 확인합니다:

   ```shell
   /opt/gitlab/embedded/bin/openssl smime -verify -binary -inform pem \
       -in /tmp/signature_text.pk7.pem -content /tmp/signed_text.txt
   ```

   이 단계가 실패하면 GitLab에서도 확인이 실패합니다.

   예를 들어 오류를 해결합니다:

   - `certificate verify error .. unable to get local issuer certificate`:
     - 신뢰 체인을 설정할 수 없습니다.
     - 이 OpenSSL 바이너리는 GitLab 신뢰 저장소를 사용합니다. 루트 인증서가 신뢰 저장소에서 누락되었거나 서명에서 중간 인증서가 누락되었으며 신뢰할 수 있는 루트로의 체인을 만들 수 없습니다.
       - 서명에 포함할 수 없는 경우 중간 인증서를 신뢰 저장소에 넣을 수 있습니다.
       - [인증서를 추가하는 절차](https://docs.gitlab.com/omnibus/settings/ssl/#install-custom-public-certificates)를 패키지된 GitLab의 신뢰 저장소에 추가합니다 - `/etc/gitlab/trusted-certs`를 사용합니다.
     - OpenSSL을 사용하여 추가 신뢰할 수 있는 인증서를 테스트합니다: `-CAfile /path/to/rootcertificate.pem`
   - `unsupported certificate purpose`:
     - 인증서는 서명자의 인증서의 `X509v3 Key Usage` 섹션에서 `Digital Signature`을 지정해야 합니다.
     - `X509v3 Extended Key Usage` (EKU) 섹션이 지정된 경우 `emailProtection`를 포함해야 합니다. 자세한 내용은 [RFC 5280](https://datatracker.ietf.org/doc/html/rfc5280#page-44)을 참조하세요:

       > (Key Usage) 확장 모두와 일치하는 목적이 없으면 인증서를 어떤 목적으로도 사용할 수 없습니다.

   - `signer certificate not found` 중 하나:
     - `-nointern` 인수를 추가했지만 `-certfile`를 제공하지 않았습니다.
     - 서명에 서명자의 인증서가 없습니다.
